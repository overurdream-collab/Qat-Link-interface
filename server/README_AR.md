# FIN-08 — مرحلة تأسيس Backend المطالبات السابقة (غير جاهزة للإنتاج)

هذه أول طبقة خادمية فعلية لمنطق **FIN-07/FIN-08**. تعمل بمعاملة PostgreSQL وتفويض اعتماداً على JWT موثّق، وتفصل سجل التاجر الأحادي عن `financial_movements`. لا تنشرها قبل ربط خدمة الهوية/OTP وتكامل Flutter والمراجعة الأمنية واختبارات الجهازين.

## ما نُفذ

- جداول PostgreSQL 16 للمخاطبين والمطالبات والمطابقة الموثقة وقرارات العملاء والعلاقات والحركات المعتمدة وسجل التدقيق. ينعزل التاجر بمرشحات خادمية مستخرجة من JWT، لا من body.
- تسجيل جهة اتصال غير مشتركة ثم مطالبات موجبة دقيقة `numeric(20,4)`، وفصل عملات YER/SAR/USD، ومنع الازدواج عبر `Idempotency-Key`.
- استقبال **إثبات هاتف موثوق من خدمة هوية خارجية** فقط؛ إتاحة كل المطالبات القديمة عبر صندوق وارد العميل دون موافقة تلقائية، مع pagination متسق وcursor موقع.
- قبول/رفض كل مطالبة؛ استقلال موافقة العلاقة. الترحيل إلى الحركة المعتمدة يتم داخل معاملة قاعدة بيانات مع قيد UNIQUE عند اكتمال الموافقتين. تم إضافة advisory transaction lock لتفادي سباق الموافقتين.
- عند إثبات ملكية الهاتف من حسابين مختلفين تُمنع رؤية المطالبات لكليهما. إلغاء الإثبات يوقف الإفصاح فوراً، دون حذف السجلات المالية.
- JWT `RS256` مع issuer/audience/sub/exp/iat/role محققة؛ لا mock auth ولا endpoint يستطيع المستخدم من خلاله منح نفسه ملكية هاتف.

## API الحالي

| الطرف | الطريقة والمسار | السلوك |
|---|---|---|
| خدمة الهوية فقط | `POST /v1/internal/merchant-profiles` | إنشاء اسم تاجر موثق |
| خدمة الهوية فقط | `POST /v1/internal/verified-phones` | تقديم إثبات هاتف بعد OTP حقيقي تم في جهة الهوية |
| خدمة الهوية فقط | `POST /v1/internal/revoke-phone-proof` | إلغاء الإثبات عند فقدان/نقل ملكية الرقم |
| تاجر | `POST /v1/merchant/contacts` | حفظ عميل في سجل التاجر فقط |
| تاجر | `GET /v1/merchant/contacts?limit=50&cursor=` | استرجاع جهات اتصاله الخاصة بترقيم صفحات موقع ومقيد بالتاجر |
| تاجر | `GET /v1/merchant/contacts/{uuid}/claims?limit=50&cursor=` | استرجاع المطالبات السابقة وحالاتها فقط من دفتر التاجر؛ لا ترحيل مالي |
| تاجر | `POST /v1/merchant/claims` | دين معلق، يجب Header `Idempotency-Key` ومبلغ decimal string |
| تاجر | `POST /v1/merchant/relationship-requests` | طلب ارتباط لعميل تأكدت مطابقته |
| تاجر | `GET /v1/merchant/claims/summary` | أرصدة الادعاءات الثلاثة بحسب العملة، وليس الرصيد المالي الكامل |
| عميل | `GET /v1/customer/relationships?limit=50&cursor=` | طلبات ارتباط جميع التجار السابقين بعد تحقق الهاتف، كل علاقة معلقة حتى موافقة العميل |
| عميل | `GET /v1/customer/previous-claims?limit=50&cursor=` | جميع طلبات التجار السابقة بحسب الإثبات |
| عميل | `POST /v1/customer/previous-claims/{uuid}/decision` | `{ "decision":"accept" }` أو `reject` |
| عميل | `POST /v1/customer/relationships/{uuid}/decision` | قرار مستقل على العلاقة |

كل العمليات المحمية تتطلب `Authorization: Bearer <RS256 JWT>` صالحاً صادراً من خدمة الهوية. `merchant_id` و`customer_id` لا يُؤخذان من طلب المستخدم. عميل غير منضم لا يستلم رسائل آلية؛ تظل المطالبة في سجل التاجر.

## التشغيل التجريبي

من جذر المستودع، جهز قاعدة PostgreSQL معزولة للتجربة، وشغّل Migration:

```bash
cd server
npm install
psql "$DATABASE_URL" -v ON_ERROR_STOP=1 -f sql/001_fin08.sql
npm run check
FIN08_TEST_DATABASE_URL="$DATABASE_URL" npm test
```

قبل تشغيل `npm start` لا بد من تحديد: `DATABASE_URL`, `AUTH_PUBLIC_KEY_PEM`, `AUTH_ISSUER`, `AUTH_AUDIENCE`, `CURSOR_SECRET` (سلسلة سرية عشوائية 32 محرفاً على الأقل), `PORT` اختياري، و`PG_SSL=true` في بيئة تتطلب TLS. **لا تنشئ JWT يدوياً في الإنتاج**؛ مزود الهوية الحقيقي هو المسؤول عن OTP والتأكد من ملكية الرقم وإصدار الأدوار. يجب أن يكون اتصال قاعدة البيانات داخل شبكة خاصة وبأقل صلاحيات.

CI الجديد `.github/workflows/fin08-api.yml` ينشئ PostgreSQL 16 مؤقتة ويجري `npm test` مع اختبار تكامل SQL. الاختبارات المحلية بلا قاعدة بيانات تشغّل فحص الأنواع والشروط والـHTTP وجلسات RS256 فقط؛ اختبار PostgreSQL يكون `SKIP` إذا غاب متغير `FIN08_TEST_DATABASE_URL`.

## الحدود المفتوحة

- لا توجد خدمة OTP/هوية فعلية ولا توكنات مستخدمين إنتاجية؛ endpoint الهوية **حدّ ثقة داخلي** وليس إثبات OTP بحد ذاته.
- لم توصل واجهات Flutter بـ API بعد، ولم يُختبر جهازان حقيقيان أو إشعارات. لا توجد مزامنة بعد إغلاق التطبيق في Flutter الحالي رغم أن تخزين هذه الخدمة دائم.
- `financial_movements` هنا خاص بديون العملاء غير المشتركين التي تحولت إلى معتمدة، وليس الدفتر الشامل للدفعات والمرتجعات والرصيد السالب. لا يجوز عرض `approved_from_claims` كرصيد التاجر الكلي.
- يلزم تقوية مطابقة الأرقام الدولية، معدل الطلبات، حماية إعادة تخصيص أرقام الجوال، نسخ احتياطي واستعادة، ومراجعة الخصوصية قبل النشر.
- لا يتم حذف/تغيير الحركات المعتمدة؛ تغييرات المحاسبة مستقبلاً تحتاج مسار تصحيح وعكس خادمي مدقّق.
## FIN-10 — طلبات الارتباط المسترجعة عند الانضمام

تقوم `reconcilePhone` بعد التحقق من ملكية الهاتف وإنشاء رابط موثوق بإنشاء طلب علاقة `pending` لكل جهة اتصال سابقة لدى تاجر. لا تُعتمد العلاقة تلقائياً؛ تظل مطالبات الدين منفصلة حتى يوافق العميل على كل مطالبة. إعادة تحقق الهاتف أو طلب التاجر لا ينشئ علاقة مكررة ولا يعيد المرفوضة إلى pending. يتطلب عرض العلاقة إثباتاً نشطاً غير متعارض.
