# FIN-13 — الدفتر الموحد: الديون والدفعات والعكس والتفويض

**المرجع:** وثيقة المواصفات المالية والمحاسبية v2.2 المقدمة بتاريخ 2026-11-17.
**تنبيه:** هذا توسيع للخادم؛ ليس إطلاقاً إنتاجياً. لا يوجد OTP فعلي متصل بالتطبيق، ولا اختبار هاتفين أو نسخ احتياطي تشغيلي.

## لماذا لا ننشئ دفترًا آخر؟
- جدول FIN-08 الحالي financial_movements يبقى **مصدر القيود المالية المعتمدة الوحيد**؛ تحفظ السجلات السابقة بأرقامها ومصادرها دون حذف أو إعادة إدخال.
- merchant_claims يحفظ الطلبات الأحادية للتاجر قبل انضمام العميل: operation_type = debt أو payment. كلاهما pending حتى إثبات العميل وموافقته على كل طلب وقبول العلاقة.
- relationship_operations يحفظ الطلبات الجديدة من طرفي العلاقة المعتمدة. منشئ الطلب يقدم إقراره؛ الطرف الآخر يوافق/يرفض، إلا عند تفويض العميل الصريح للديون المستقبلية.
- اعتماد عملية واحدة ينتج **قيداً واحداً فقط** عبر مفتاح المصدر الفريد. الرفض لا ينشئ قيداً.
- جميع المبالغ تستخدم PostgreSQL NUMERIC(20,4) وسلاسل Decimal وBigInt scale 10,000؛ لا float ولا جمع للعملات.
- القيد المعتمد غير قابل لتحديث أو حذف من قاعدة البيانات عبر trigger؛ التعويض يتم بطلب عكس مستقل ثم موافقة الطرف الآخر ثم قيد ذي أثر مقابل.

## الترحيل دون فقد البيانات

التسلسل الإلزامي:
1. نسخة احتياطية مجربة وإجراء نافذة نشر قبل ترقية إنتاجية لاحقة.
2. تطبيق server/sql/001_fin08.sql للمثيل الجديد، أو التأكد من تطبيقه مسبقاً.
3. تطبيق server/sql/002_fin13_unified_ledger.sql مرة واحدة؛ التغييرات إضافية وتحافظ على source_claim_id والقيود القديمة، داخل معاملة واحدة.
4. التحقق من إجماليات الحساب على عينة مالية قبل/بعد، ثم تشغيل اختبارات PostgreSQL.
5. API دون صلاحية DDL؛ migrator بصلاحية منفصلة. النسخ الاحتياطي والاستعادة الفعلية **لم ينفذا** هنا.

## API — المصادقة JWT والأدوار merchant/customer

| الفعل | الطريقة والمسار | الضمان |
|---|---|---|
| إنشاء عملية جديدة | POST /v1/relationships/{id}/operations | type=debt/payment؛ Idempotency-Key؛ pending افتراضياً |
| قرار الطرف الآخر | POST /v1/relationships/{id}/operations/{operationId}/decision | accept/reject؛ الترحيل داخل معاملة |
| قائمة عمليات العلاقة | GET /v1/relationships/{id}/operations | ترقيم صفحات موقّع ومقيد بالدور والعلاقة |
| تفويض العميل | POST /v1/customer/relationships/{id}/auto-approval | enabled boolean؛ الخادم وحده يقرر |
| استعلام التفويض | GET /v1/relationships/{id}/auto-approval | الحالة، الإصدار، التواريخ |
| طلب عكس قيد معتمد | POST /v1/relationships/{id}/reversals | movement_id + reason؛ pending حتى الموافقة |
| أرصدة معتمدة | GET /v1/relationships/{id}/balances | ثلاث عملات: debts/payments/net؛ من القيود |
| كشف معتمد | GET /v1/relationships/{id}/statement?currency=YER&from=YYYY-MM-DD&to=YYYY-MM-DD | افتتاحي/ختامي حسب آسيا/عدن |
| دفعة خارج التطبيق | POST /v1/merchant/claims | type=payment + contact_id,amount,currency,Idempotency-Key |

- occurred_at هو تاريخ العملية الأصلي بتوقيت صريح، منفصل عن created_at وتاريخ الترحيل posted_at. الرصيد التاريخي يعتمد تاريخ الترحيل: دين أقدم اعتُمد اليوم لم يكن ضمن رصيد الشهر الماضي.
- تفويض الديون التلقائي OFF افتراضياً؛ العميل وحده يفعله لعلاقة approved. يسلسل الخادم تعديل السياسة وإنشاء العملية بقفل العلاقة ورقم إصدار؛ لا يشمل إلا **ديناً جديداً يسجله التاجر بعد التفعيل**، ولا الديون السابقة ولا الدفعات أو العكس.
- دفعات العميل تحتاج موافقة التاجر، ودفعات التاجر تحتاج موافقة العميل، ودون ذلك تبقى معلقة.
- الرصيد السالب رصيد دائن لصالح العميل.
- الكشف المعتمد لا يضم pending/rejected، وإذا تجاوز 500 قيد في الفترة يرد خطأ واضح ولا يعيد كشفاً جزئياً؛ الحد 367 يوماً شاملاً، والتصفح الطويل مهمة لاحقة.
- سجل التدقيق fin08_audit_events وسجل التفويض relationship_policy_events. عند إلغاء دليل الهاتف تتوقف سلطة العميل وفق سياسة الإثبات ويبقى السجل محفوظاً للتاجر.

## الاختبار المالي القياسي

1. قبل الانضمام: دين 20,000 YER + دين 15,000 YER + دفعة 10,000 YER؛ خارج التطبيق: ديون 35,000، دفعات 10,000، رصيد معتمد 0.
2. بعد إثبات الهاتف وموافقة العميل على العلاقة والدين الأول والدفعة فقط: صافي **10,000 YER**؛ الدين الثاني pending.
3. دفعة أخرى معتمدة بقيمة 20,000 YER تجعل الرصيد **-10,000 YER**؛ دائن للعميل.
4. تفعيل التفويض لا يمس الدين القديم؛ إيقافه يجعل الديون الجديدة يدوية.
5. العكس يُنشئ قيداً مقابلًا ولا يحذف أصل الحركة.
6. استقلال YER/SAR/USD؛ منع التكرار، وعزل التجار، ومراجعة مصدر أي قيد.

## أعمال غير مكتملة بعد هذه المرحلة

- OTP حقيقي وربط جلسات Flutter والهوية الإنتاجية.
- الموافقات الجماعية الانتقائية وطلب تعديل مبلغ pending، والتسويات المتقدمة والتخصيص.
- حدود الائتمان والإشعارات والمزامنة دون اتصال.
- كشف PDF خادمي وتوصيل واجهات التاجر والعميل النهائية.
- UAT على هاتفين، استعادة نسخ احتياطية، وتدقيق أمني قبل التشغيل الحقيقي.
- خدمة هوية تعالج نقل ملكية رقم الهاتف والأرقام المعاد تخصيصها.

**مهم:** approved_from_claims في ملخص FIN-08 ليس رصيداً شاملاً؛ استخدم /balances لكل علاقة وعملة. لا تدّع اكتمال منتج مالي كامل قبل سد البنود المذكورة.
