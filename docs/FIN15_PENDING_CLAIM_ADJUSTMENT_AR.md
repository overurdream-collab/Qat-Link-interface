# FIN-15 — تعديل مبلغ مطالبة معلقة دون المساس بالأصل أو الرصيد

**المرجع:** مقتني لنك — المواصفات المالية والمحاسبية v2.2، القسم 10.
**النطاق:** ديون ودفعات سجلها التاجر في merchant_claims وظهرت للعميل الموثق، ولم يتخذ بشأنها قرارًا بعد. لا يشمل تعديل قيد معتمد؛ المعتمد يستخدم مسار العكس FIN-13.

## الرحلة الصحيحة
1. يراجع العميل مطالبة سابقة، ويرى المبلغ الأصلي والعملة والوصف والتاريخ.
2. يطلب مبلغًا مختلفًا موجبًا وسببًا واضحًا. يحفظ الطلب مستقلًا في customer_claim_adjustment_requests (pending)، ويوقف قبول أو رفض المطالبة القديمة إلى حين القرار.
3. يراجع التاجر مبلغ المطالبة الأصلي ومقترح العميل؛ يمكنه رفض الاقتراح فتعود المطالبة الأصلية للمراجعة، أو قبوله.
4. إذا قبله، يحتفظ الخادم **بالمطالبة الأصلية دون تغيير مبلغها**، ويضع عليها superseded_by_claim_id، وينشئ مطالبة جديدة بالمبلغ المقترح مع source_claim_id يشير للأصل، وبنفس العملة ونوع العملية وتاريخ وقوعها. تبقى الجديدة UNACKNOWLEDGED حتى يقرر العميل قبولها بصورة مستقلة.
5. لا تُرحّل أي مطالبة superseded أو pending adjustment، ولا يؤثر طلب التعديل على المعتمد إطلاقًا.
6. إذا أكمل العميل قبول الجديدة والعلاقة approved، يرحّل الخادم قيدًا واحدًا إلى financial_movements. كل إعادة محاولة محمية بقاعدة UNIQUE وسجل تدقيق.

## الأمن والقيود
- الخادم يستمد customer/merchant من JWT ولا يسمح بتغيير العلاقة أو هوية عميل بالـbody.
- customer_phone_evidence وverified_contact_links يخضعان لفحص ملكية الهاتف **عند كل طلب وقرار وتسجيل قيد**؛ عند فقد إثبات الهاتف يُمنع الوصول/الإقرار.
- معاملة ذرية تتسلسل مع FIN-08/FIN-14 بقفل أزواج التاجر/العميل ثم صف المطالبة. لا تسمح بالموافقة الجماعية أثناء طلب تعديل pending لأن FIN-14 يستدعي ensureEligible المشتركة.
- لا يُقبل اقتراح مساوي للأصل، أو مبلغ صفري/سلبي، أو سبب فارغ، أو أكثر من طلب pending للهوية ذاتها.
- الاعتماد الآلي للديون المستقبلية FIN-13 لا يشمل مطالبات التعديل التاريخية.
- يُسترجع تاريخ العملية occurred_at القديم في المطالبة الجديدة، مع created_at جديد لتتبع تاريخ الطلب. كشف الرصيد التاريخي يعتمد posted_at فقط.

## API
- POST /v1/customer/previous-claims/{claimId}/amount-adjustment
  - Body: proposed_amount decimal string, reason.
  - Return: adjustment_id, claim_id, status=pending، replayed.
- POST /v1/merchant/claim-adjustments/{adjustmentId}/decision
  - Body: decision=accept|reject.
  - Return: status=accepted|rejected, source_claim_id, replacement_claim_id (قبول فقط)، replayed.
- GET /v1/customer/previous-claims: حالات جديدة awaiting_merchant_adjustment / superseded وpending_adjustment_id/proposed_amount وsource_claim_id.
- GET /v1/merchant/contacts/{id}/claims: الحقول والحالات نفسها مقيدة بالتاجر.
- GET /v1/merchant/claims/summary: يستبعد المطالبات superseded من المبالغ المعلقة لمنع عد المبلغ الأصلي والجديد مرتين. المعتمد يبقى من القيد الحقيقي لا المبلغ التقديري.

## اختبارات القبول
- طلب تعديل يوقف قرار قبول الأصل، بما في ذلك موافقة FIN-14 الجماعية.
- رصيد مشترك لا يتغير أثناء المقترح المعلق، رفض التاجر، أو قبول الاقتراح مع إنشاء الطلب البديل.
- أصل الطلب يُحفظ بالمبلغ والتاريخ والعملة، والبديل يشير إليه ويحتاج موافقة العميل.
- طلب ثاني مختلف أثناء وجود pending يفشل، والإعادة المتطابقة لا تكرر الطلب.
- بعد قبول الطلب البديل مع اعتماد العلاقة يترحل مبلغ البديل مرة واحدة فقط.
- دفعة تاريخية تخضع للآلية نفسها وتُنقص الرصيد فقط بعد اعتمادها.
- عزل التاجر والعميل وإبطال إثبات الهاتف يمنع الوصول.
- لا يتغير approved financial_movements المانع للتعديل/الحذف الصامت.

## غير مشمول أو لم يُختبر إنتاجيًا
- اقتراح تعديل مبلغ طلب جديد في relationship_operations؛ يتطلب مسار تغيير موثق مستقل.
- OTP/JWT الحقيقي والأجهزة وإشعارات Push وPDF والدفعات غير المتصلة والتسويات المتقدمة.
- النسخ الاحتياطي التشغيلية، UAT جهازين، النسخ إلى production. لا تدع CI تعني تشغيلًا إنتاجيًا.
