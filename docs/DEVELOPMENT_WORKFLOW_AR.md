# سياسة التطوير وضمان التوثيق المستمر

**الغرض:** إنجاز ميزة قابلة للتسليم دون إعادة اكتشاف القرارات أو ترك وثائق متعارضة. هذه السياسة إجرائية على مستوى المستودع، ولا تدعي وجود حوكمة آلية كاملة.

## قبل بدء أي تغيير

1. قراءة آخر main وPRs المفتوحة وحالة CI والملفات ذات الصلة.
2. تحديد المطلب الموافق عليه، الهدف العملي، الميزة المتأثرة، وإصدار المواصفات الحالي. لا تُدخل وظائف أخرى بالتخمين.
3. كتابة «قبل/بعد»، والأدوار المسموح لها، وحالة النظام عند فشل الشبكة أو تكرار الضغط أو إغلاق نافذة الحجز أو رفض العميل.
4. تأكيد أثر التغيير على المعادلة المالية والموافقات والعملات والحقوق والاشتراكات وخصوصية العملاء، حتى لو كان «لا أثر».
5. إنشاء فرع مستقل من آخر main ولا تعدل main مباشرة. لا تغير ملفات مبنية من فرع آخر متعارض.

## أثناء التنفيذ

- ضع منطق المجال في خدمات أو دوال نقية عندما يمكن؛ اجعل الواجهة تعرض النتائج ولا تتخذ قرارات أمان غير موثقة.
- احرص على وجود عنصر UI يمكن اختباره (Key واضح عند الحاجة)، وعلى وجود حالات نجاح وفشل ورفض وتحميل.
- لا تستخدم بيانات زائفة على أنها حقيقية ولا تؤكد حجزاً أو إرسالاً عند غياب Backend.
- لا تؤثر الحجوزات أو الإشعارات أو الصور على أرصدة الأموال.
- لا تستهدف عملاء خارج علاقة التاجر أو دون تفضيل إشعار موثق.
- لا تُسقط موافقات الطرف الثاني، ولا تمزج العملات أو تتجاهل السالب.
- حافظ على واجهات RTL والترويسة والشريط السفلي والثيم المعتمد، وفي المكونات الفرعية استخدم الإطار المشترك.

## ماذا يوثّق مع كل ميزة؟

| العنصر | ما يكتب |
|---|---|
| هدف الميزة | المشكلة الأصلية وقيمتها للتاجر/العميل |
| رحلة المستخدم | قبل/بعد؛ كل زر وخطوة وقرار وإشعار |
| نماذج/حالات | هوية/صلاحية/مدة/مبلغ/عملة/موافقات؛ الحالات الفارغة والأخطاء |
| الملفات | كل ملف جديد أو معدل، علاقته بالمكونات الأخرى |
| سبب الاختيار | لماذا هذه الآلية؟ ما الذي يمنع تكرار الإدخال أو المخاطر؟ |
| الاختبارات | مسارات الاختبارات ونتائج كل اختبار آلي أو يدوي تم فعلاً |
| ما لم ينفذ | API أو قاعدة بيانات أو إشعار أو جهاز/تصميم لم يتصل بعد |
| روابط التنفيذ | PR وSHA ورابط GitHub Actions، بعد توفر النتائج |
| التعارض | اسم الوثيقة الأقدم والنص الذي نسخه القرار الجديد |

## دورة PR

- افتح PR بوصف دقيق يستعمل [.github/PULL_REQUEST_TEMPLATE.md](../.github/PULL_REQUEST_TEMPLATE.md).
- حدّث الوثيقة المرجعية للميزة (لا تضف وثيقة مكررة بلا داع)، [سجل القرارات](DECISION_LOG_AR.md)، [حالة التنفيذ](IMPLEMENTATION_STATUS_AR.md)، والفهرس إن تغيّر.
- شغّل flutter pub get وflutter analyze --no-fatal-infos وflutter test أو راقب نفس الخطوات في GitHub Actions.
- إذا فشل الاختبار: اقرأ السجل وعالج السبب الأصلي ثم أعد الفحوص؛ لا تغيّر توقع الاختبار لإخفاء خلل السلوك.
- لا تدمج PR قبل نجاح الخطوات الضرورية. لا تدع الاختبارات الآلية تقنعك بأن اتصال Push/قاعدة/إنتاج قد اكتمل.
- راجع Diff الذي سيدمج، ثم ادمج فقط SHA الذي اجتاز الفحوص؛ تحقق من تشغيل CI على main أيضاً.
- وثق بعد الدمج: commit، رابط التشغيل، عدد/حالة الاختبارات، وأي اختبار جهاز غير منفذ.

## شروط القبول للتغييرات الحساسة

**الديون والموافقات:** اختبار طلب معلّق دون أثر، موافقة الطرف الثاني، رفض، عدم تكرار، العملاء المتشابهون، العملة، الرصيد السالب، وربط التاجر الصحيح.

**الحجوزات:** اختبار التاجر المغلق، ساعات من–إلى و24 ساعة، نافذة عبر منتصف الليل، العميل غير المرتبط، الحجز المكرر، فشل الإرسال، ومرة واحدة لإجراء التأكيد.

**التذكير:** اسم التاجر الموثق، الصنف/الوقت/العدد، موافقة استلام الإشعارات، كتم التذكير، تقسيم الجمهور، احتساب فتح واحد لكل شخص، وعدم تحويل النقر إلى حجز أو دين وهمي.

**التصدير والمشاركة:** كشف PDF صحيح بالعربية، بدون تسرب أسعار/هواتف للعمال، ومراجعة الأجهزة المخصصة.

**الباقات:** لا تتغير الحقوق المالية بسبب الاشتراك؛ أي قيد تجاري يستند إلى قرار مكتوب وقاعدة خادمية، لا زر معطل فقط.

## تسليم المبرمج التالي

قبل تسليم أي نسخة: أرفق [دليل التسليم](DEVELOPER_HANDOVER_AR.md)، [جدول الحالة](IMPLEMENTATION_STATUS_AR.md)، آخر PR/Commit ونتائج Actions، تعليمات تشغيل التطبيق، قائمة المخاطر والواجهات غير المتصلة، والقرار المطلوب من صاحب المشروع إن وجد.

**الصدق في الحالة جزء من الجودة:** «مكتمل منطقياً»، «مختبر آلياً»، «متصل بالخادم»، «مختبر على جهاز»، و«جاهز للإنتاج» حالات مختلفة.
