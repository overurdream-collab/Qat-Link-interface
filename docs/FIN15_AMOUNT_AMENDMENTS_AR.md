# FIN-15 — طلب تعديل مبلغ الدين قبل الاعتماد

**المصدر:** المواصفات المالية والمحاسبية للدفتر المشترك v2.2، الفصل 10.
**الحالة:** خادم PostgreSQL وFlutter UI/API منفذان مع اختبارات CI، لكن غير جاهزين للإنتاج قبل OTP وUAT ونسخ احتياطي مجرّب.

## القاعدة المحاسبية
لا يمكن للعميل أو التاجر تغيير مبلغ دين معتمد أو حذف قيد معتمد. إذا اختلف العميل مع دين معلق، يطلب مبلغًا جديدًا ويذكر السبب. تحتفظ قاعدة البيانات بالمبلغ الأصلي وبالمبلغ المقترح وبصاحب الطلب وبقرار التاجر وتوقيته. لا يتغير الرصيد المعتمد أثناء انتظار تعديل المبلغ.

- العميل الموثق فقط يطلب تعديل **دين** سابق مسجل من التاجر أو دين حديث أنشأه التاجر في علاقة معتمدة؛ لا تنطبق هذه الموافقة على الدفعات أو التسويات أو القيود المعتمدة.
- يمنع الخادم موافقة الدين الأصلي، فردياً أو جماعياً، أثناء انتظار رد التاجر على التعديل.
- رفض التاجر: يبقى الدين الأصلي معلقًا دون تغيير؛ للعميل أن يوافق أو يرفض أو يقدم اقتراحًا جديدًا لاحقًا.
- قبول التاجر: يحتفظ النظام بالأصل، ويضع علامة أنه استُبدل دون تعديل قيمته، ثم يُنشئ مطالبة/عملية **جديدة ذات مرجع للأصل** بالمبلغ المقترح؛ طلب العميل بالمبلغ الجديد وقرار التاجر الصريح يشكلان اعتماد المبلغ الجديد. لا يدخل الرصيد إلا إذا كانت العلاقة معتمدة واستمرت صلاحية هوية العميل.
- التفويض التلقائي لا يقرر التعديلات؛ كل قبول يتم بطريقة يدوية موثقة. لا يُحسب المبلغ الأصلي والمبلغ البديل معًا.
- تظل قيود financial_movements غير قابلة للتعديل أو الحذف؛ العكس للمعتمد عبر FIN-13.

## قاعدة البيانات
تضاف بعد 001 و002 Migration 003: server/sql/003_fin15_amendments.sql.

الكيانات المضافة: financial_amendment_requests تحتوي على معرف الأصل (مطالبة تاريخية أو عملية حديثة، أحدهما فقط)، المبلغين بــ NUMERIC(20,4)، العملة، السبب، تاريخ الطلب، حالة pending/accepted/rejected، صاحب الرد، معرف البديل، ومفتاح Idempotency-Key. يُمنع تزامن اقتراحين مفتوحين للأصل الواحد، وتبقى المحاسبة مبنية على financial_movements وحده.

- merchant_claims.superseded_by_claim_id يشير إلى المطالبة البديلة؛ يظل المبلغ الأصلي للتوثيق، ولا يمكن ترحيله بعد الاستبدال.
- relationship_operations.status يضيف superseded، والبديل يشير إلى replaces_operation_id؛ يحتفظ بالسجل الأصلي.

## REST API
كلها تلتزم بالتحقق من JWT والتفويض حسب الدور، ولا تقبل هوية طرف من body:
- POST /v1/customer/previous-claims/{claimId}/amendments — body: proposed_amount كسلسلة Decimal موجبة، reason (3–500 حرف)، header: Idempotency-Key.
- POST /v1/relationships/{relationshipId}/operations/{operationId}/amendments — عميل العلاقة الموثق فقط.
- GET /v1/customer/amendments — الطلبات التي أرسلها العميل، مع صفحات ومؤشرات موقعة.
- GET /v1/merchant/amendments — طلبات تخص هذا التاجر فقط.
- POST /v1/merchant/amendments/{amendmentId}/decision — body: decision accept أو reject؛ لا توجد موافقة تلقائية.

تتم عمليات قبول التعديل وإنشاء البديل والتحقق من الهوية وترحيل القيد عند استيفاء الشروط في معاملة PostgreSQL واحدة. أي خطأ يؤدي إلى ROLLBACK. يمنع تكرار الاعتماد بقيد UNIQUE لكل مصدر ومفاتيح idempotency.

- طلب تغيير 20,000 YER إلى 18,000.5000 مع بقاء الأصل، وعدم إدراجه عند انتظار قبول العلاقة.
- منع الموافقات العادية والجماعية أثناء التعديل.
- عدم تسريب طلب تعديل بين التجار، وعدم قبول صاحب رقم مختلف.
- قبول التاجر ينشئ بديلًا واحدًا ويعتمد وفق العلاقة، ولا يغير مبلغ الأصل.
- رفض التاجر يعيد إتاحة الدين الأصلي للموافقة المستقلة.
- دين حديث 50 SAR يصبح 47.2501 SAR بعد موافقتي العميل والتاجر، مع ترحيل واحد فقط.
- التعديل والقرار المعاد إرسالهما لا يُكرران أي قيد.

## ما لم ينفذ
هذا المسار لا يسمح بتعديل قيد معتمد؛ يتطلب العكس كما في FIN-13. لا تنفذ هذه المرحلة حد الائتمان أو تسوية الدفعات أو الباقات أو التصدير الكامل، ولا تعالج تغير مالك رقم الهاتف دون خدمة هوية موثوقة. ربط الواجهات يحتاج مصادقة JWT حقيقية؛ لا تُستخدم واجهة PIN المحلية كتوثيق.

**تحذير تشغيلي:** لا تُطبق 003 على قاعدة بيانات إنتاجية قبل تجربة الترحيل والاستعادة من نسخة احتياطية، وتقييد حساب تطبيق API بالصلاحيات اللازمة فقط.
