# FIN-09 — استرجاع سجل التاجر وربط واجهات Flutter بعقد FIN-08

**التاريخ:** 2026-11-16  
**السبب:** بعد FIN-08 أصبحت المطالبات محفوظة خادمياً، لكن لم يكن للتاجر API لاسترجاع قائمة جهات الاتصال والمبالغ عند إغلاق التطبيق أو تغيير جهازه، ولم تكن هناك طبقة Flutter HTTP قابلة للاختبار تستعمل جلسة موثقة.

## ما يقدمه هذا التغيير

1. `GET /v1/merchant/contacts?limit=50&cursor=` يرجع جهات اتصال **التاجر صاحب JWT فقط** مع صفحات محفوظة بترتيب `(created_at,id)` وتوقيع HMAC للـcursor وربطه بالتاجر والنطاق. لا يقبل `merchant_id` من الاستعلام.
2. `GET /v1/merchant/contacts/{uuid}/claims?limit=50&cursor=` يرجع كل مطالبة خاصة بجهة الاتصال لهذا التاجر فقط؛ الخطأ `404` لجهة اتصال لا يملكها. تعرض كل مطالبة تاريخها، المبلغ كنص Decimal، العملة والحالة التالية: `outside_app`، `awaiting_review`، `accepted_awaiting_relationship`، `accepted_awaiting_posting`، `approved`، `rejected`. منذ 2026-11-22 تعيد أيضًا `relationship_id` و`relationship_status` عند وجود علاقة، ليتمكن التاجر من فتح دفتر FIN13 للعلاقة المعتمدة. لا تتغير موافقات العميل أو الرصيد في طلبات GET.
3. **Flutter gateway** في `lib/services/fin08_api_client.dart` يستعمل `package:http` مع `http.Client` قابل للحقن للاختبارات، وتوكن من مزود هوية موثوق عند كل طلب، ولا يخزن رقم PIN أو JWT أو مبالغ محلياً. يرفض HTTP غير المشفر خارج localhost، ويميز فشل الشبكة وفشل الصلاحيات والتعارض.
4. `Fin08CustomerClaimsScreen` لعرض مطالبات العميل الموثق السابقة من كل التجار مع تحميل الصفحات، موافقة/رفض مستقلة وحوار تأكيد، ثم **استرجاع الحالة من الخادم** بدل الموافقة المتفائلة.
5. `Fin08MerchantBookScreen` لاسترجاع سجل التاجر، عرض المبالغ **بكل عملة مستقلة**، إضافة جهات الاتصال والديون المعلقة عبر API، مع مفتاح عدم تكرار عشوائي ثابت طيلة نافذة إدخال الدين ومحاولة إعادة إرساله.

## أهم الضمانات

- هوية التاجر والعميل تُشتق خادمياً من JWT صادر بعد OTP حقيقي. **لا توجد مصادقة أو OTP إنتاجية في المشروع بعد.** لم يُربط أي من الشاشتين بشاشة تسجيل الدخول؛ لا دخول زائف، ولا صلاحيات ناتجة من رقم هاتف مكتوب.
- تستمر المطالبات القديمة عند التاجر بعد إعادة تشغيل العميل **فقط عند تشغيل الخادم وقاعدة PostgreSQL حقيقةً**؛ `AppState` الحالي يبقى ذاكرة مؤقتة، ولا يُقدم كحفظ دائم.
- مبلغ المطالبة المعلقة ليس ديناً معتمداً، والموافقة على العلاقة لا توافق تلقائياً على جميع المطالبات، ولا تجمع العملات. `approved_from_claims` محدود بالديون القديمة وليس صافي الرصيد الكامل بما فيه المدفوعات.
- لا إرسال فعلي عبر واتساب، ولا دفع أو تسديد في خادم FIN-08 حتى هذه المرحلة؛ الرفض يُحفظ ولا يحذف سجلات التدقيق.
- لا مشاركة لمطالبات التاجر عبر رابط عام؛ يحتاج كل طلب دور merchant ومسار ملكية صريحاً. كل cursor موقع ومقيد بالتاجر/القائمة.
- `POST /v1/merchant/claims` يعيد 200 عند إعادة المحاولة بنفس `Idempotency-Key` وبنفس البيانات؛ يحتفظ النموذج المقترح بالمفتاح حتى إعادة المحاولة في نافذة الإدخال.

## التحقق المطلوب

- `cd server && npm run check && FIN08_TEST_DATABASE_URL="$DATABASE_URL" npm test` مع تطبيق `server/sql/001_fin08.sql` في PostgreSQL 16 المؤقتة.
- `flutter pub get && flutter analyze --no-fatal-infos && flutter test` على CI للمشروع.
- فحوص: منع قراءة حساب تاجر آخر، وعدم تبديل cursor بين تجار/قوائم، انتقال outside_app إلى awaiting_review دون أثر مالي، رفض، اعتماد دين محدد بعد علاقتين، تأكيد أن `Idempotency-Key` ثابت، بقاء الطلب معلقاً عند خطأ اتصال.

## حدود الإنجاز وما يلزم قبل التجربة على جهازين

**الشاشتان قابلة للحقن وليستا متصلتين بـmain/Login بعد.** الربط النهائي يستلزم: خدمة هوية/OTP حقيقية تنشئ JWT بأدوار موثقة، قاعدة بيانات حقيقية وبيئة HTTPS، جلسة آمنة وصلاحيات استعادة/تسجيل الخروج، وإحالة المستخدم إلى شاشة التاجر أو العميل وفق دور الجلسة؛ ثم تجربة جهازين وإغلاق/فتح التطبيق مع فشل الشبكة واختبار الخصوصية. لا يُطلق التطبيق على أنه جاهز للإنتاج قبل ذلك.

الملفات الأخرى في `main` والهوية البصرية السابقة لم تتغير، ولا توجد حركات معتمدة جديدة ينشئها واجهتا FIN-09 دون موافقة العميل.
