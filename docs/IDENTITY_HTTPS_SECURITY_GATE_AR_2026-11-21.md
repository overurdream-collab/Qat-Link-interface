# بوابة أمان نشر Identity عبر HTTPS — مراجعة 21-11-2026

**الحالة المحدثة: بوابة localhost ومسارات الهوية وOTP تعمل (5/5 PASS)، لكن النشر الخارجي وفتح OTP ما زالا BLOCKED.** نتائج الفقرات التاريخية أدناه تخص الوضع قبل تحديث Caddy وOTP؛ لا تستخدمها لتمثيل الحالة الحية الحالية.

## أدلة اختبارات فعلية
- الوصول من Caddy إلى `http://identity:8090/healthz`: `{"status":"ready"}`، exit 0.
- Caddy مستقل على `fin25-test-net` باستخدام `deploy/fin25/Caddyfile.identity-smoke-test`: `HEALTH=200`، `ME=401` بدون جلسة، `FAKE_PROOF=400`، `OTP=403`.
- Cloudflare Quick Tunnel الخارجي: TLS verify = 0 (صالحة للشهادة المقدمة عند حافة Cloudflare)، `GET /v1/identity/me = 404`، `GET /v1/auth/otp/request = 403`، و`POST /v1/auth/otp/request = 403`.
- Caddy المحلي: `POST /v1/auth/otp/request = 403`. لا ترسل الاختبارات السابقة SMS.
- شهادة Origin الحالية محلية `CN=localhost` مع SAN `localhost`,`127.0.0.1` وتاريخ انتهاء 2026-11-24. Tunnel يستعمل `--no-tls-verify` في **الجزء الداخلي بين cloudflared وCaddy**. هذا لا يثبت تحقق TLS على الأصل؛ يُحظر اعتماده مسار إنتاج نهائيًا.
- **ملاحظة تاريخية superseded:** كانت Caddy الحية تعيد 404 لمسارات Identity قبل التحديث، لكن المستخدم أثبت بعد نشرها `GET /healthz=200` و`GET /v1/identity/me=401` و`POST /v1/auth/otp/public-request=503` (مغلق افتراضيًا)، إلى جانب حظر proof الخارجي.

## نتائج مراجعة مصدر الكود (وليست اختبارات اختراق)
1. `server/src/identity_server.mjs`: يحد حجم JSON بـ4096 بايت، يتحقق من content-type، ويفحص OTP عبر FIN25، ويرفض الجلسة دون إثبات صالح؛ **لا يوجد حد طلبات صريح لكل عنوان/جهاز/حساب على `POST /v1/identity/session`** في هذا الملف. تأمين الحافة ضرورة قبل التوجيه العام.
2. `server/src/fin25_otp_transport.mjs`: يظهر حد 5 طلبات/ساعة للهاتف وفاصل 60 ثانية في قاعدة البيانات لمسار طلب OTP؛ **لا يغني عن تحديد المعدل حسب IP/جهاز، وقواعد منع إساءة الاستخدام، والسيطرة على تكلفة الرسائل عند حافة الشبكة**.
3. `deploy/fin25/Caddyfile`: `remote_ip 127.0.0.1 ::1` يخص عنوان العميل الذي يراه Caddy داخل الحاوية؛ لا تُفترض سلامته خلف Docker/Cloudflare، ويجب فحصه عمليًا على staging.
4. `deploy/fin25/Caddyfile.identity-smoke-test` يستخدم HTTP داخليًا، ولا ينشر منفذًا في إعداد اختبار الحاوية الذي ثبت نجاحه؛ **ليس بوابة HTTPS عامة**.
5. `IDENTITY_API_BASE_URL` يُقرأ وقت بناء Flutter ويشترط `https`. `FIN25_OTP_BASE_URL` يُقرأ وقت البناء للشاشات التجريبية. بناء GitHub العام لم يمرّر هذه العناوين صراحةً؛ لا يصح اعتباره جاهزًا للتسجيل الحي.

## بوابات قبول مطلوبة قبل النشر
- [ ] إثبات **اسم مضيف عام دائم وشهادة HTTPS موثوقة** وحماية TLS بين الحافة والأصل، دون الاعتماد على Quick Tunnel العام أو شهادات localhost، مع الحفاظ على Caddy الحالي وعدم إنشاء بوابة أخرى.
- [ ] حماية `POST /v1/identity/session` بضوابط معدل موثوقة عند الحافة وخلفها، تحترم هوية المصدر (لا `X-Forwarded-For` غير موثوق)، مع استجابة 429 وآليات منع الإساءة.
- [ ] إضافة اختبارات آلية للحجم غير الصحيح والطرق غير المسموحة وJWT غير الصالح والإثبات المعاد/المستهلك، وإثبات عدم تسرب بيانات الأسرار/الهواتف في السجلات.
- [ ] مراجعة تصميم OTP ضد الرسائل المتكررة، وحماية المسارات الداخلية `/v1/internal/otp/proof` وواجهات الإدارة وتسجيل الجهاز، والتأكد من عدم إمكان الوصول الخارجي إليها.
- [ ] اعتماد خطة دخول OTP للهاتف قائمة على rate limiting فعال وتفويض موثق، لا إزالة `403` مباشرة.
- [ ] بناء APK اختبار بعناوين HTTPS موثوقة، مع مراجعة التوقيع وSHA256، ثم تجربة الهاتف عبر بيانات اصطناعية/اختبار وموافقة مالك الخدمة.
- [ ] إثبات تنفيذ FIN08 مع Identity الفعلي في staging وليس محاكاة HTTP، والالتزام بالموافقة الثنائية قبل أي قيد مالي.
- [ ] فحص أسرار Git بما فيها تاريخ الالتزامات قبل الدمج في `main`؛ مراجعة PR #71 وقضايا الإصدار والأمن.
